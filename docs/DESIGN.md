# pkcm-agent — 설계 원칙과 로드맵

Pokémon Champions 배틀 시뮬레이터 + 에이전트. 개인 사이드 프로젝트.

목표는 세 개다.

1. Champions 룰(Regulation Set M-B)을 따르는 **정확한 배틀 시뮬레이터**
2. 그 위에서 도는 **탐색 + 학습 하이브리드 배틀 정책**
3. **파티 구성까지 학습** — 종족 선택, 기술 4개, 도구, 특성, Stat Alignment, SP 배분

2번이 1번의 설계를 규정한다. 아래 원칙은 그 제약에서 나온 것이고, 편의를 위해 어기면
나중에 엔진을 다시 써야 한다. 3번은 2번을 평가 함수로 쓰는 바깥 루프다 (§6).

## 1. 아키텍처 원칙

### (a) 상태는 값이고, `step`은 순수 함수다

```
step(state, action_p1, action_p2) -> (state', events)
```

전역 상태·싱글턴·I/O 없음. ISMCTS는 한 수를 두기 위해 상태를 수천 번 복제하므로
**clone 비용이 곧 탐색 깊이**다. Showdown처럼 가변 객체 그래프로 짜면 탐색을 못 붙인다.

### (b) RNG는 상태의 일부이고 밖에서 주입한다

난수 스트림을 `state`에 담고 명시적으로 전진시킨다. 그래야:

- 완전 재현 (버그 리포트 = 시드 하나)
- 같은 상황 다른 주사위 롤아웃 (탐색의 전제)
- 급소/추가효과/명중을 기대값으로 접는 근사 (탐색 가지치기)

### (c) 진실(ground truth)과 정보집합(info set)을 처음부터 분리한다

```
BattleState                     실제 상태 (양쪽 전부 알고 있음)
Observation(state, player)      그 플레이어가 아는 것만
determinize(obs, rng) -> State  관측과 모순 없는 진실 하나를 샘플링
```

포켓몬은 상대의 지닌물건·기술 4개·노력치·후발 3마리가 전부 은닉정보다. 이걸 나중에
붙이려 하면 엔진 전체를 다시 써야 한다. **하이브리드 정책의 생사가 여기 달려 있다.**

### (d) 메커니즘은 이벤트 훅, 데이터는 외부

특성·도구·필드·상태이상이 전부 같은 계산 단계에 끼어든다(`ModifyDamage`, `BeforeMove`,
`OnSwitchIn`, ...). 거대한 if 사슬이 아니라 **우선순위 있는 이벤트 버스**로 간다.
이 부분은 Showdown의 설계가 옳아서 구조만 차용한다.

### (e) 엔진은 렌더링을 모른다

엔진은 구조화된 이벤트 로그(`Damage`, `Faint`, `SwitchIn`, `Boost`, ...)만 뱉는다.
텍스트 뷰어든 PokéAPI 스프라이트 렌더러든 그 로그를 소비하는 별도 모듈이다.

### (f) PettingZoo는 어댑터지 엔진이 아니다

```
pkcm/engine/   순수 함수 코어. 탐색이 여기 직접 올라탄다.
pkcm/envs/     PettingZoo ParallelEnv 어댑터. 엔진을 감싸기만 한다.
```

학습 파이프라인은 `envs/`를, 탐색은 `engine/`을 직접 쓴다. PettingZoo가 주는 표준 API와
래퍼 생태계는 챙기면서 탐색 성능은 안 버린다.

**AEC가 아니라 ParallelEnv**를 쓴다. 포켓몬은 진짜 동시행동 게임이라 AEC로 직렬화하면
두 번째 에이전트가 첫 번째의 행동을 보는 정보 누출을 매 턴 손으로 막아야 한다.
기절 후 강제교체처럼 한쪽만 행동하는 턴은 **행동 마스크 + NOOP**으로 처리한다
(`infos[agent]["action_mask"]`).

### (g) "합법인가"와 "우리가 구현했는가"는 다른 질문이다

`legality.py`는 *챔피언스가 이 팀을 허용하는가*를 묻고, `scope.py`는 *우리 엔진이 이걸
충실히 실행할 수 있는가*를 묻는다. 둘은 서로 다른 권위에 답하고 서로 다른 속도로 바뀐다 —
하나는 닌텐도가 레귤레이션을 바꿀 때, 다른 하나는 우리가 마일스톤을 끝낼 때.

이걸 합치면 조용한 재앙이 된다. 엔진이 아직 못 돌리는 기술이 "불법"이 되고, M1이 올라가는
날 팀 합법성이 학습된 정책 아래에서 소리 없이 바뀐다.

그래서 엔진은 실행 못 하는 기술을 만나면 **아무 일도 없었던 척하지 않고** 어떤 메커니즘이
빠졌는지 로그에 남긴다(`unimplemented` 이벤트). 랜덤 팀 생성기는 그런 기술을 애초에 뽑지
않는다 — no-op으로 처리되는 기술로 자가대전을 돌리면 정책은 "그 기술은 공짜"라고 배운다.

## 2. 데이터 레이어

두 층으로 쌓는다.

| 층 | 위치 | 출처 | git |
|---|---|---|---|
| upstream | `data/raw/` | Pokémon Showdown 클라이언트 데이터 | ignored (재생성) |
| curated | `data/champions/` | Bulbapedia 레귤레이션 + 손으로 쓴 룰 상수 | 커밋 |

**override 레이어는 필수다.** (한때 "거의 필요 없다"고 적었으나 틀렸다.) Showdown의 base
데이터는 스칼렛/바이올렛이고, 챔피언스는 그것과 상당히 다르다:

| | |
|---|---|
| 기술 | base가 "표준"이라 부르는 685종 중 **194종이 챔피언스에 없다.** 실제 풀 500종 |
| 기술 수치 | ~30종의 위력·명중·PP·타입이 다름 (부리찌르기 120, 성장이 풀타입 등) |
| PP | 기본 PP **20 상한**, 최대 PP는 `(pp/5+1)*4` — 시리즈의 `pp×8/5`가 아님 |
| 도구 | 181개 제거, 76개 추가 |
| 상태이상 | 마비 1/8, 잠듦 2~3턴, 얼음 3턴 타이머 + 1/4 해동 |
| 클로즈 | 종족·아이템에 더해 **잠듦기술·일격필살·회피** 클로즈 |

이 델타의 출처는 **Showdown 저장소의 `data/mods/champions/`** 다. Showdown이 챔피언스를
모드로 구현해 두었고, 그게 우리가 가진 챔피언스 메커니즘의 가장 정확한 명세다.

```bash
python scripts/fetch_showdown_data.py         # data/raw/*.json (클라이언트 수치)
python scripts/fetch_showdown_source.py       # data/reference/*.ts (구현 참조)
python scripts/build_champions_overrides.py   # data/champions/overrides.json
python scripts/fetch_regulation.py m_b        # data/raw/regulation_m_b.wikitext
python scripts/build_champions_data.py        # data/champions/regulation_m_b.json
```

override 빌더는 **선언적 델타만** 추출한다 (존재 여부, 위력, 명중, PP, 타입). 핸들러 함수를
덮어쓰는 항목은 `needs_hand_port`에 이름이 남고, TypeScript를 읽고 파이썬으로 옮기는 건
사람이 한다. 자동 번역은 하지 않는다.

## 3. 룰 (Regulation Set M-B)

확인된 것:

| 항목 | 값 |
|---|---|
| 팀 | 6마리 등록 → 팀 프리뷰 → 선출 |
| 레벨 | 전원 50 자동 보정 |
| 아이템 | 중복 불가 |
| 종족 | 중복 불가 |
| 메가진화 | 허용, **배틀당 1회** |
| 테라스탈 | **없음** (M-B 룰 텍스트에 부재) |
| 시간 | 게임 20분 / 플레이어 7분 / 턴 45초 / 프리뷰 90초 |
| 출전 | 235종 + 메가 76종 |
| 싱글 | 6 → 3 |
| 더블 | 6 → 4 |

### 능력치: SP 체계

Champions는 시리즈의 EV/IV 모델을 버렸다.

| | 기존 시리즈 | Champions |
|---|---|---|
| 개체값 | 0~31 | **폐지** — 전원 31 상당으로 고정 |
| 노력치 | EV 508 총량 / 252 상한 | **SP 66 총량 / 32 상한** |
| 환산 | EV 4 = 실능력치 +1 | **SP 1 = 실능력치 +1** |
| 성격 | 25종 (중립 5) | **Stat Alignment 21종** (중립은 Serious 하나) |

레벨 50 고정이라 고전 공식이 이렇게 접힌다:

```
HP    = Base + 75 + SP
그 외 = floor((Base + 20 + SP) × alignment)
```

주의할 점은 **SP가 안쪽 floor 바깥에 더해진다**는 것이다. EV처럼 안으로 접히지 않기
때문에 "SP 1 = 정확히 +1"이 성립한다. `tests/test_stats.py`가 접힌 식과 원식을
1~255 전 구간에서 대조해 이 단순화를 지킨다.

구현은 `pkcm/engine/stats.py`. 레벨 50이 아니면 예외를 던진다 — 오프레벨에서 SP가
어떻게 스케일되는지는 근거가 없고, Champions는 물어보지 않는다.

## 4. 구현 현황

마일스톤을 하나씩 게이팅하지 않는다. 목표는 "포챔스와 동일한 게임"이므로 메커니즘을 대량으로
붓는다. 다만 특성·도구·상태이상·필드가 전부 같은 계산 지점에 끼어들기 때문에 **훅 골격을 먼저**
세웠다 — 개별 특수처리로 쌓으면 나중에 전부 다시 써야 하니까.

### 되는 것

턴 루프, 팀 프리뷰(6→3), 선공 판정(우선도 → S → 동속난수, 트릭룸 반전), 데미지 공식,
타입 상성, 급소(랭크 무시 포함), 명중(랭크 반영), PP, 발버둥, 교체, 기절/강제선출, 승패.

랭크 변화 7종, 상태이상 6종(타입 면역 포함), 혼란·풀죽음·방어(연속 사용 실패율)·대타출동·씨뿌리기,
날씨 4종, 필드 4종, 트릭룸, 벽 3종, 바람타기, 설치기 4종.

기술 효과는 **데이터에서 직접 읽는다** — `boosts`, `status`, `volatileStatus`, `secondary(ies)`,
`self`, `drain`, `recoil`, `heal`, `multihit`, `sideCondition`, `weather`, `terrain`,
`pseudoWeather`, 고정 데미지, 일격필살. 가변 위력은 11종 구현.

**표준 기술 685종 중 510종(74.5%)** 을 실행한다.

### 특성

`data/reference/abilities.ts`를 **읽어서** 옮긴다. 기억으로 재구성하지 않는다 — 그렇게 쓴
초안은 등록만 하고 아무것도 안 하는 핸들러를 여럿 포함하고 있었다.

M-B 로스터의 특성 201종 중 **198종 구현, 출전 슬롯의 99%**.
남은 3종(되새김질·숙성·점착)은 전부 **지닌물건에 작용**하는 것이라 도구가 들어오기 전에는
구현할 수 없다. 등록하지 않고 두는 것이 커버리지 리포트가 그렇게 말하게 하는 방법이다.

`scripts/ability_report.py`가 구현 형태별로 묶어 남은 것을 보여준다 — 201종이 110여 형태로
줄어서, 특성 단위가 아니라 형태 단위로 옮길 수 있었다.

프레임워크를 구부린 세 가지:

| 특성 | 왜 특별한가 | 어디에 들어갔나 |
|---|---|---|
| **틀깨기** | 기술 해결 *내내* 상대 특성이 안 보여야 함 | `ctx.suppressed_abilities` — 훅 수집 자체가 참조. "각 면역 검사마다 틀깨기 확인"은 반드시 빠지는 곳이 생긴다 |
| **부식** | 강철/독의 면역을 *공격자*가 뚫음 | `set_status`가 **source** 쪽 `status_immunity` 훅을 통과시킴. 게다가 독 타입 기술이 강철에 닿아야 하므로 `modify_effectiveness`도 함께 |
| **포이즌힐** | 막는 게 아니라 **뒤집음** | 간접 데미지 전부를 `apply_damage`의 `modify_indirect_damage` 한 곳으로 모음. 매직가드도 같은 훅 |

그리고 상당수가 같은 것을 요구했다: **기술을 이번 사용에 한해 다시 쓰기** (Showdown의
`onModifyMove`). `ActiveMove`가 그 자리다 — 페어리스킨이 타입을 바꾸고, 스킬링크가 타격수를
고정하고, 원격이 접촉을 지우고, 틈새포착이 벽을 통과하고, 우격다짐이 포기하는 추가효과를
실제로 지운다.

데미지 배율은 Showdown과 같이 **4096분의 고정소수점**(`chain_modify`)으로 계산한다.
소스가 실제로 `chainModify([5325, 4096])`이라 적혀 있고, float로 하면 확정수 계산이 어긋난다.

**"무엇인가"를 바꾸는 것에는 수명이 있다.** 변환자재의 타입 변경, 변신, 트레이스가 빌린 특성,
배틀스위치의 폼은 전부 **필드를 떠나면 되돌아간다** (그래서 변환자재는 재등장하면 다시 1회
충전된다). 반면 메가진화와 깨진 탈은 배틀이 끝날 때까지 남는다. 그래서 `state.overrides`의
각 항목은 `__permanent__`로 남을 키를 명시하고, 교체 시 나머지는 지워진다.

**메타몽의 괴짜/변신이 동작한다.** 상대의 현재 폼·특성·타입·능력치(HP 제외)·기술(각 PP 5)과
**랭크 변화까지** 복사한다. hk가 보고한 시나리오는 이제 `mega-evolution` 하나만 기다린다.

### 도구

목록의 출처가 특별하다. **op.gg에서 긁은 실제 게임의 도구 화면**(`포챔스 아이템 목록.txt`)이고,
Showdown의 챔피언스 모드보다 최신이다 (모드는 커뮤니티 이식이라 뒤처질 수 있다).

**147개 = 배틀 도구 72 + 메가스톤 75.** 스톤 75개가 M-B 합법 메가 76종을 전부 커버한다
(냐오닉스나이트 하나가 암수 두 폼을 담당).

스크랩 파서에서 한 번 틀렸던 지점을 남겨둔다: 출처(source) 값을 `Shop`/`Beginning`/`Event`로
하드코딩했더니, 출처가 `Mega Evolution Tutorial`이거나 `Deposit <x> from Pokemon Legends: Z-A`인
**11개 항목의 블록 경계를 놓쳐 앞뒤 항목이 합쳐졌다.** 스톤 12개가 목록에 없는 것처럼 보였고,
"합법 메가로부터 추론"이라는 불필요한 보정까지 만들었다. 지금은 "다음 줄이 가격 형태인가"로
블록 끝을 판정한다 — 열거하지 말고 구조를 읽을 것.

챔피언스가 무엇을 **잘라냈는지**가 메타의 핵심이다:

| 남음 | 잘림 |
|---|---|
| 구애스카프 | **구애머리띠, 구애안경** |
| 먹다남은음식, 생명의구슬, 기합의띠 | 돌격조끼, 진화의휘석, 고무플레이트 |
| 열매 29종, 타입강화 18종 | 먹밥부츠, 약점보험, 화염구슬, 맹독구슬, 풍선 |

두 출처(op.gg 스크랩과 Showdown 모드)가 **잘린 목록에 대해 완전히 일치**한다.

배틀 도구 72개 전부 구현. 도구가 요구한 새 장치: 도구 소비(영구), 구애 락(`legal_actions`가
읽음), 필드 지속시간 훅(날씨 바위·빛의점토), `dealt_damage`(생명의구슬·조개껍질방울·왕의징표석),
`update` 체크포인트(열매가 HP/상태를 지켜보는 자리).

### 아직 안 되는 것

메가진화, 2턴 기술, 교체 유발 기술, 카운터 계열, 더블배틀.
그리고 데이터에 효과가 없는 기술들.

### 성능

단일 코어 3,900 turns/s (144 battles/s). 훅 골격 도입 전 11,000에서 내려온 값이고,
그만큼 실제로 메커니즘이 돌고 있다.

## 5. 검증 전략

**최종 정답지는 챔피언스 본편이고, 명세서는 Showdown의 champions 모드다.**

두 가지를 구분해야 한다.

- **차분 테스트 오라클로서의 Showdown**: 폐기. 두 엔진을 같은 시드로 돌려 로그를 비교하는
  건 Node가 필요하고, base 엔진은 어차피 SV라 챔피언스 고유 동작에서 갈린다.
- **명세서로서의 Showdown 소스**: 채택. `data/mods/champions/`는 챔피언스 구현 그 자체이고,
  MIT 라이선스다. 특성·도구·상태이상의 동작을 **기억으로 재구성하지 않고 소스를 읽어서**
  옮긴다. 실제로 그렇게 해서 마비 확률·잠듦 지속·PP 공식·기술 194종 부재를 전부 바로잡았다.

그래도 최종 권위는 게임이다. 모드도 커뮤니티 구현이라 틀릴 수 있고, 챔피언스가 패치되면
갱신이 늦을 수 있다. 그래서 관찰을 영구 테스트로 만드는 장치를 함께 둔다.

### 시나리오 (`tests/scenarios/`)

게임에서 본 동작을 JSON 한 파일로 적는다 — 상황, 취한 행동, 관찰된 결과. 자세한 형식은
`tests/scenarios/README.md`.

핵심 성질은 **구현 전에 먼저 적어도 된다**는 것이다. 각 시나리오는 필요한 메커니즘을
`requires`에 선언하고, 엔진이 아직 없는 걸 요구하면 **실패가 아니라 이유와 출처를 밝히며
skip**된다.

```
SKIPPED  needs abilities, mega-evolution, stat-stages, transform
         (recorded from: Pokemon Champions, reported by hk)
```

관찰이 마일스톤을 기다리다 유실되지 않는다. 메커니즘을 구현하는 커밋에서
`pkcm/testing/scenario.py`의 `IMPLEMENTED`에 이름을 추가하면 대기하던 시나리오가 스스로
켜져서 검증을 시작한다. 이게 §1(g)의 합법성/구현범위 분리와 같은 원리다.

보조 수단: 불변식 property test (HP는 음수가 될 수 없다, PP는 단조 감소한다, 랜덤 자가대전은
항상 종료한다), 그리고 접힌 공식과 원식의 전 구간 대조 (`tests/test_stats.py`).

## 6. 파티 구성 학습 (바깥 루프)

배틀 정책이 "주어진 팀으로 어떻게 싸우나"라면, 이건 "애초에 어떤 팀을 가져가나"다.
두 문제는 분리되지 않는다 — 팀의 좋고 나쁨은 **그 팀을 쓰는 정책의 승률**로만 정의되고,
정책의 최적 행동은 팀에 의존한다.

### 결정 공간 (M-B 실측)

한 마리를 확정하는 데 필요한 결정:

| 결정 | 규모 |
|---|---|
| 종족 | 235 (팀 6마리, 종족 중복 불가) |
| 기술 4개 | 배우는 기술 중앙값 83종 → C(83,4) ≈ **184만** |
| 특성 | 1~3 (235종 중 125종이 3개) |
| 도구 | 팀 내 중복 불가 |
| Stat Alignment | 21 |
| SP 배분 | 합 ≤ 66, 각 ≤ 32 → **1억 3,666만** |

SP 공간은 고전 EV(508/252, 61억)보다 **45배 작다**. 그래도 절대적으로는 크다.
한 슬롯의 조합만 이미 천문학적이고, 팀은 그게 6개다.

### 두 가지 함정

**(1) 고정 상대 풀에 대한 과적합.** 팀을 고정된 상대 집합에 맞춰 최적화하면 그 집합에만
강한 카운터 팀이 나온다. 메타게임은 본질적으로 가위바위보라, 단일 최적 팀이란 게 없다.
population 기반(PSRO 계열)으로 상대 풀 자체를 같이 키워야 한다.

**(2) 평가 노이즈.** 팀 A가 팀 B보다 나은지 판정하려면 배틀을 여러 번 돌려야 하는데,
포켓몬은 분산이 크다. 팀 하나 평가에 드는 배틀 수가 곧 바깥 루프의 비용이다.
배틀 시뮬레이터의 처리량이 여기서 다시 병목이 된다.

### 설계 방향 (미확정)

파티 구성을 **순차적 구성 MDP**로 본다. 빈 팀에서 시작해 결정을 하나씩 놓고
(종족 → 도구 → 특성 → 기술 → alignment → SP), 완성된 팀을 배틀 정책으로 평가해
보상을 받는다. 이러면 밴픽/드래프트와 같은 구조가 되고, 부분 팀 상태에 대한 가치함수를
학습할 수 있다.

SP 배분처럼 연속에 가까운 결정은 전부 열거하지 않고 **템플릿 + 미세조정**으로 접는 것을
검토한다 (예: 최대 투자 2스탯 선택 → 남은 SP 배분). 여기는 아직 열려 있다.

**핵심 전제**: 바깥 루프는 배틀 정책을 평가 함수로 호출한다. 따라서 §1(a)의
"clone이 싸야 한다"는 제약이 여기서도 그대로 걸린다.
